# Plan Implementation

If you are incapable of long horizon tasks or not a frontier model, please let the user know it and stop. You should be able to process the following using a sufficient context window. 

This skill systematically generates a eloborate todo list like plan for smaller models to follow. We are not generating code but generate advice and steps for a small model to follow. Think of you like a teacher model where the instructions generated by this skill are executed by a child model. Child can be a full model or a subagent.

Guide the child to follow the generated plan do the agentic implementation of any part of this software. Child should work on a single feature at a time within a single bounded context (bc). 

Now first perform the `before plan` phase. If succeded move to `commit plan` phase.

### Before Plan

- Check if `.agents/discover/conventions.md` file exists.
  - If exist: Load the conventions and use them for instructions.
  - If not exist: Create a one at the end of the skill execute.
- Definition: We call `.agents/specs/{bc}/domain-model.md` as the *domain spec* for a given bc
- Load the bounded context: read *domain spec* with `adr*.md` files and `.agents/discover/context-map.md` for cross-context relationships. 
  - If *domain spec* doesn't exist:
    - ask the user to run the `bcdiscovery` and `compilespec` skills before calling this skill and stop.
  - If *domain spec* exist:
    - after reading below point proceed to `commit plan`.
- Stop and request approval when an architectural decision is ambiguous or unresolved. DO NOT PROCEED. Examples of "ambiguous or unresolved":
  - The spec conflicts with the bounded context canvas (e.g. asks to write data owned by another context)
  - The work implies a dependency or integration crossing a context boundary not documented in the context map
  - The requirement has more than one valid interpretation and the choice affects the data model, API shape, or context ownership
  - A needed decision was flagged `[Needs Human]` in the bounded context discovery and hasn't been answered


### Commit Plan

1. Again make sure you loaded, *domain spec* with `adr*.md` files and `.agents/discover/context-map.md` for cross-context relationships. 
2. Only follow the specification. Load both spec and todo list in the context.
3. Honour established conventions in `.agents/discover/conventions.md`
4. Make sure plan instruct to make small, reviewable changes.
5. Record any deviations from the spec (in the spec file or a linked note).
6. Use following impl order: Value type -> Entities -> Domain services -> App Services
7. Create a file in `.agents/progress/{bc}/implementation-plan.md`
8. Implementation Plan writing steps:
  - Write coding instructions preamble for the child. Eg: Coding conventions, style, rules etc considering above. Also for test running instruct following:
      - If tests pass, continue.
      - If tests fail: attempt a fix within the spec's scope and re-run, up to 2 attempts.
      - If still failing after 2 attempts, or the fix would require deviating from the spec, stop and report the failure to the user rather than proceeding further.
  - Write a instruction to read `Agents.md` file at root.
  - Then in the above order (Step 6.) for each item,
    LOOP {

    - Create an instruction to Generate structs, interfaces and other types for the current item as a todo item set. You can decide how much todo items are needed considering granularity of the item.
    - Create instruction to stop the model and wait the user to say proceed. User will review child's code.
    - Create an instruction to write unit test suite for the item with a todo item set on proceed above.    
    - Create instruction to stop the model and wait the user to say proceed.
    - Create instructions on creating the methods or functions for this item that satisfies the unit tests as a todo item set.    
    - Instruct to Run the tests and verify
    - Create instruction to stop the model and wait the user to say proceed. User will review child's code. Instruct child to tell the name of the next item to be implemented before stop. When user says proceed child should move to next item.

    }
    UNTIL while all items are documented.
  
- Optional : Write an ADR to `.agents/specs/{bc}/planimpl-agent-adr-{date}.md` for any significant architectural decision made during implementation.

### After Commit Plan

- Identify unresolved risks and produce a summary in `.agents/progress/{bc}/planimpl-output-{date}.md`.
- Ask the architect to review. Stop and wait for feedback — do not start a new feature or spec until review is complete.
