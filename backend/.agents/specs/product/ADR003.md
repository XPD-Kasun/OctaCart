# Category Modelling

Use Materialized Path Hierarchy with Dot Notation for Category Trees

# The Problem

How to represent and persist category hierarchy in the database to allow efficient traversal and subtree queries.

# Options Considered

- **Single root hierarchy tree with dot-separated path persistence (Materialized Path)**
- Recursive CTE with parent ids
- Separate parent-child table with other metadata like depth
- Nested sets

# Rationale

Materialized dot-separated paths (e.g., `1`, `1.2`, `1.3`) provide fast read lookups for subtree queries and ancestor resolution without recursive joins, while laying groundwork for native PostgreSQL `ltree` indexing in the future. Also, since Cateogry is a hierarchial data structure we needed a high level presentation for this to use for certain use cases.

For example:

```go
type CatNode struct{
  Cat
  Parent *CatNode
}
```

We identified following are the most common workflows.

1. Breadcrumb Rendering
2. Category selection by the user like a menu
3. Generating SEO friendly URLs involving Cats
4. Filtering such as in a product listing
5. Merchant admin category creation, deletion and assignment ...etc

For above 1,3,4 an array of categories works (array contains a single hierarchy or list of cats of same depth). For 2 and 5, a hierarchial repr like above CatNode is needed.

First we consider Category has following structure,

```go
type Category struct {
    ID        int64
    Name      string
    Slug      string
    ParentID  *int64 //nullable for root
    Path      string // "1.2.3"
    Depth     int
    SortOrder int
}
```

Therefore, we use a flat list in the repo return types.

We can use the following algorithm to convert a cat list to a `CatNode`.

```go
func CatTree(cats []*Cat): *CatNode {
  var cache map[int]*CatNode
  var rootCat *CatNode = &CatNode{}

  for _, a := range cats {
    catNode := &CatNode{a}
    if cn, ok := cache[a.ParentId]; ok {
      catNode.Parent = cn
    } else {
      catNode.Parent = rootCat
    }
  }
  return rootCat
}
```

Repo needs have following methods, other than usual, create, update, delete

```go
GetById(ctx, id) ->*Cat
GetChildren(ctx, id)-> []*Cat
GetAncestors(ctx, id) -> []*Cat
GetSubtree(ctx, id) -> []*Cat
Move(ctx, id, parentId) -> error
GetDepth(ctx, depth int) -> []*Cat
```

# Notes

Categories can also specify attribute specifications (attribute name, type, required status) that automatically become part of products assigned to that category.
