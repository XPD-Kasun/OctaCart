## Step 1 — High-Level Domain Map

### Actors
| Actor | Role |
|---|---|
| Shopper | Submits reviews for products they have purchased; edits or withdraws own reviews; views published reviews and rating summaries |
| Admin | Moderates submitted reviews: approves or rejects from a queue; may add a moderation note on rejection |
| Reporting BC | Consumes ReviewPublished and ReviewRejected domain events for analytics and reporting pipelines |

### Key Flows

**Flow 1 — Shopper submits a review**
1. Shopper buys a product → order delivered
2. Shopper calls SubmitReview with productId, optional orderId, rating (1-5), and review body
3. Review BC verifies purchase via OrderVerificationPort (if orderId provided) → sets isVerifiedPurchase
4. Review is persisted with status = Submitted
5. Admin moderation queue receives the review
6. Admin approves → status = Published → ReviewPublished event emitted
7. Published review appears on the product storefront

**Flow 2 — Admin moderates**
1. Admin fetches moderation queue (ListPendingModeration)
2. Admin reads review body and decides: Approve or Reject
3. ApproveReview → Submitted → Published; ReviewPublished event published
4. RejectReview(reason) → Submitted → Rejected; ReviewRejected event published

**Flow 3 — Shopper views product reviews and rating summary**
1. Storefront calls GetProductRatingSummary(productId) → returns RatingSummary (avg, count, distribution)
2. Storefront calls ListReviewsByProduct(productId, filter, page) → returns paginated Published reviews

## Steps 3-4 — Boundary Analysis & Classification

### Why NOT Product BC
- Product BC would need to know about Customer (author) and Order (verified purchase), creating upward dependencies that pollute the product catalog.
- Different rates of change: product titles and prices change rarely; reviews stream in daily with their own moderation lifecycle.
- Moderation is a dedicated workflow that has nothing to do with catalog management.

### Why NOT Customer BC
- A review is fundamentally about a product, not the shopper's profile.
- Customer BC does not own product-related data or moderation workflows.

### Why NOT Order BC
- Order BC concerns itself with purchase records, fulfillment, and payments.
- Reviews are created after fulfillment; the Order BC's only role is a read-only verification check (HasDeliveredOrderForProduct), not review storage.

### Classification: Supporting
The Review BC supports the core purchasing experience (Product + Order) but is not itself a revenue-generating or order-processing concern. It is well-defined, has a stable lifecycle, and can be built from well-known patterns → **Supporting**.

## Step 5 — Ubiquitous Language

### Glossary

| Term | Definition |
|---|---|
| Review | A structured piece of feedback (rating + body) submitted by a customer about a product they purchased |
| Rating | An integer score 1-5 stars attached to a Review |
| Verified Purchase | A Review linked to a confirmed delivered order for that product; marked isVerifiedPurchase=true |
| Moderation | The admin workflow of approving or rejecting Submitted reviews |
| ReviewStatus | The lifecycle state of a Review: Submitted \| Published \| Rejected \| Withdrawn |
| RatingSummary | Read-only projection: {avgRating float64, totalCount int, distribution map[1..5]int} for one product |
| Withdrawal | Shopper-initiated removal of their own review (Submitted or Published → Withdrawn) |
| ReviewVote | A Helpful/NotHelpful signal cast by a customer on a Published review [Assumed — deferred to post-v1] |
| Moderation Note | Optional free-text reason attached by admin when rejecting a review |

### Polysemes

| Term | In Review BC | In Other BC |
|---|---|---|
| Review | Structured customer feedback entity with lifecycle | Not a concept in Product, Customer, or Order BCs |
| Rating | Integer 1-5 score on a Review | Not a concept in Product BC (product may have price, not rating) |
| Order | A foreign-key reference (orderId) used only for verified purchase verification | In Order BC: the full purchase record including lines, status, payment |
| Status | ReviewStatus (Submitted/Published/Rejected/Withdrawn) | In Order BC: OrderStatus (different states entirely) |

## Step 7 — Validation (2 Scenarios)

### Scenario 1: Shopper submits a verified review
1. Shopper calls `SubmitReview(customerId=42, productId=7, orderId=99, rating=5, body="Great product!")`
2. Review BC checks for duplicate: `ReviewRepo.FindByProductAndCustomer(7, 42)` → nil → no duplicate
3. Review BC calls `OrderVerificationPort.HasDeliveredOrderForProduct(ctx, 42, 7)` → `true`
4. Sets `isVerifiedPurchase = true`, `status = Submitted`
5. Persists via `ReviewRepo.Save(review)`
6. No shared tables with Order, Product, or Customer BCs → ✅ boundary respected
7. ReviewSubmitted event emitted → **OK**

### Scenario 2: Admin moderates and Reporting consumes
1. Admin calls `ApproveReview(reviewId=101)`
2. `ReviewStatusMachine.Transition(Submitted → Published)` → valid
3. Review is updated: `status = Published`, `publishedAt = now()`
4. `ReviewRepo.UpdateStatus(101, Published)`
5. `EventPublisher.Publish(ReviewPublished{reviewId:101, productId:7, customerId:42, rating:5, isVerifiedPurchase:true})`
6. Reporting BC consumes event via in-process event bus
7. Product BC has zero involvement → ✅ boundary respected → **OK**

### Application Services

#### ReviewSvc
```
SubmitReview(ctx, customerId shared.UserId, productId int, orderId *int, rating int, title *string, body string) -> (Review, error)
```
- Validates rating ∈ [1,5] → ErrInvalidRating
- Validates body non-empty → ErrBodyRequired
- Checks duplicate: FindByProductAndCustomer → ErrAlreadyReviewed if Submitted or Published exists
- Calls VerifiedPurchaseChecker if orderId != nil → sets isVerifiedPurchase
- Sets status = Submitted, submittedAt = now()
- Saves via ReviewRepo
- Errors: ErrAlreadyReviewed, ErrInvalidRating, ErrBodyRequired

```
EditReview(ctx, reviewId ReviewId, customerId shared.UserId, title *string, body string) -> (Review, error)
```
- Only allowed while status = Submitted
- Validates ownership → ErrNotReviewAuthor
- Errors: ErrReviewNotFound, ErrNotReviewAuthor, ErrReviewAlreadyPublished, ErrBodyRequired

```
WithdrawReview(ctx, reviewId ReviewId, customerId shared.UserId) -> error
```
- Shopper withdraws own review (Submitted or Published → Withdrawn)
- Validates ownership → ErrNotReviewAuthor
- Errors: ErrReviewNotFound, ErrNotReviewAuthor, ErrInvalidTransition

#### ModerationSvc
```
ApproveReview(ctx, reviewId ReviewId) -> error
```
- Transitions Submitted → Published
- Sets publishedAt = now()
- Publishes ReviewPublished event
- Errors: ErrReviewNotFound, ErrInvalidTransition

```
RejectReview(ctx, reviewId ReviewId, reason string) -> error
```
- Transitions Submitted → Rejected
- Sets moderationNote = reason
- Publishes ReviewRejected event
- Errors: ErrReviewNotFound, ErrInvalidTransition

#### ReviewVoteSvc *(Deferred — post-v1)* [Assumed]
```
VoteOnReview(ctx, reviewId ReviewId, customerId shared.UserId, vote VoteKind) -> error
```
- Idempotent; updates helpfulCount on Review aggregate

```
RemoveVote(ctx, reviewId ReviewId, customerId shared.UserId) -> error
```

#### ReviewQuerySvc

GetReview(ctx, reviewId ReviewId) -> (Review, error)

### Domain Services

#### ReviewStatusMachine
Enforces legal ReviewStatus transitions:

| From | To | Trigger |
|---|---|---|
| Submitted | Published | ApproveReview |
| Submitted | Rejected | RejectReview |
| Submitted | Withdrawn | WithdrawReview |
| Published | Withdrawn | WithdrawReview |

All other transitions → ErrInvalidTransition

#### VerifiedPurchaseChecker
Calls `OrderVerificationPort.HasDeliveredOrderForProduct(ctx, customerId, productId) -> bool`
Sets `review.isVerifiedPurchase` accordingly at submission time. Stateless.

#### RatingSummaryCalculator
Aggregates Published reviews for a product into a RatingSummary:
- avgRating = sum(rating) / count(Published reviews)
- distribution = map[rating]count for ratings 1-5
- [Assumed] Computed on-the-fly at small scale; cached if performance requires it [Needs Human: caching strategy]
