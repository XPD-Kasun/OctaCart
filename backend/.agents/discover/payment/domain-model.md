## Step 1 — High-Level Domain Map

### Actors
| Actor | Role |
|---|---|
| Shopper | Initiates payment at checkout; redirected to gateway payment page |
| Admin | Triggers refunds via back-office REST API |
| Order BC | Upstream caller — triggers InitiatePayment with orderId + amount |
| External Payment Gateway | Stripe / Razorpay / COD — processes funds and fires webhooks |

### Flows

**Flow 1 — Payment Initiation (happy path)**
1. Shopper completes checkout → Order BC places order
2. Order BC calls `Payment.InitiatePayment(orderId, amount, currency)`
3. Payment BC creates `Payment` record (status: `Initiated`)
4. Payment BC calls `PaymentGatewayPort.CreateCheckoutSession` → receives `(sessionToken, checkoutUrl)`
5. Payment BC returns `checkoutUrl` to Order BC / REST driving adapter
6. Shopper is redirected to gateway-hosted payment page and pays
7. Gateway fires webhook `POST /webhooks/payment/:gateway`
8. `PaymentWebhookHandler` verifies gateway signature → calls `OnPaymentCaptured` or `OnPaymentFailed`
9. `OnPaymentCaptured` → transitions Payment to `Captured` → publishes `PaymentCaptured`
10. Order BC reacts to `PaymentCaptured` (transitions order `Pending → Paid`) [Inferred]

**Flow 2 — Refund (Admin)**
1. Admin calls `POST /api/v1/payments/:id/refund` with `{amount, reason}`
2. `PaymentRestHandler` authenticates via Auth BC (JWT/session) → calls `PaymentSvc.RefundPayment`
3. `RefundAmountValidator` checks total refunds do not exceed captured amount
4. Payment BC calls `PaymentGatewayPort.RefundCharge(gatewayRef, amount)`
5. Creates `Refund` record (`Issued`) → updates `Payment` status (`Refunded` or `PartiallyRefunded`)
6. Publishes `RefundIssued` → Order BC and Reporting BC react

## Step 3-4 — Boundary Analysis & Classification

### Primary Heuristic: PCI DSS Security / Regulatory Perimeter
Payment credentials, gateway tokens, session tokens, and transaction records must be isolated from all other BCs. Even though OctaCart does not store raw card data (the gateway handles it), the gateway integration and the full transaction audit trail belong behind a dedicated payment boundary. This prevents accidental co-mingling of payment concerns with order or customer logic.

### Secondary Heuristics
| Heuristic | Observation |
|---|---|
| **Different rate of change** | Payment gateway APIs change on gateway release schedules; order logic changes on business schedules. Isolating them prevents gateway upgrades from destabilising Order BC. |
| **Different domain expert** | Payment / finance team owns Payment BC; order management team owns Order BC. Different vocabulary, different compliance concerns. |
| **Regulatory / audit** | Payment records require audit-trail durability and may be subject to financial regulations independent of order records. |
| **Swappable adapter** | The ACL pattern (StripeGatewayAdapter) ensures that switching gateways is a driven-adapter swap, not a domain model change. |

### Classification
**Supporting** — Commodity payment processing. Not OctaCart's competitive differentiator. Strategy: integrate via well-known gateway; do not innovate here. Could be replaced by a third-party payment service if needed.

## Step 5 — Ubiquitous Language with Polysemes

### Glossary
| Term | Definition |
|---|---|
| Payment | A transaction record representing the full money-movement lifecycle for one order; created when initiation is triggered and updated through capture, failure, or refund |
| Checkout Session | A gateway-created temporary session that redirects the shopper to the gateway-hosted payment page; has a short-lived `sessionToken` and a `checkoutUrl` |
| Capture | The gateway confirming that funds have been received; transitions a `Payment` from `Initiated` to `Captured` |
| GatewayRef | The external transaction identifier assigned by the payment gateway (e.g., Stripe charge ID `ch_xxx`); used to correlate webhook events back to internal Payment records |
| Refund | A partial or full reversal of a `Captured` payment; recorded as a separate `Refund` entity; may set Payment status to `Refunded` or `PartiallyRefunded` |
| Webhook | An HTTP callback from the payment gateway notifying OctaCart of a payment status change (captured, failed, etc.); must have its signature verified before processing |
| PaymentStatus | Lifecycle enum: `Initiated` | `Captured` | `Failed` | `Refunded` | `PartiallyRefunded` |
| RefundStatus | Lifecycle enum: `Pending` | `Issued` | `Failed` |
| GatewayStatus | ACL-internal enum translating gateway webhook status to OctaCart concepts: `Pending` | `Succeeded` | `Failed` |
| GatewayAdapter | The ACL component that translates between the OctaCart Payment domain model and the external gateway API; swappable per gateway |

### Polysemes (Same Word, Different Models)
| Term | Payment BC | Other BC | Resolution |
|---|---|---|---|
| **Method** | Payment instrument or gateway type (card, UPI, COD) | Shipping BC: delivery option | Different concepts — no shared type; each BC owns its own enum [Inferred] |
| **Amount** | Transaction amount in minor units (shared.Money) | Order BC: grandTotal — used as *input* to InitiatePayment but owned by Order | Passed by value at initiation; Payment BC does not replicate Order's amount model |
| **Status** | PaymentStatus enum | Order BC: OrderStatus; Shipping BC: ShipmentStatus | All different types; explicit naming prevents confusion |
| **Session** | Checkout Session (gateway-generated, shopper-facing) | Auth BC: user session / JWT | Completely different concerns; named CheckoutSession within Payment BC |

## Step 6 — Relationships Between Contexts

| Upstream | Downstream | Pattern | Notes |
|---|---|---|---|
| Order | Payment | Customer-Supplier | Order supplies orderId + grandTotal + currency when initiating payment; Payment is the downstream consumer. Order must not change this contract without coordinating with Payment. |
| Auth | Payment | OHS/PL | Admin identity verification for refund and query endpoints; Payment consumes Auth's published JWT/session validation. Stable published language. |
| Payment | Order | OHS/PL | Payment publishes PaymentCaptured / PaymentFailed events consumed by Order. Payment defines and owns the event schema (stable published language); Order conforms. |
| Payment | Reporting | Customer-Supplier | Reporting consumes PaymentCaptured, PaymentFailed, RefundIssued, RefundFailed events. Payment is upstream supplier. |
| External Gateway | Payment | ACL | StripeGatewayAdapter (or equivalent) translates between OctaCart's Payment domain model and the gateway's external API. The ACL protects the Payment domain from gateway API volatility. |

## Step 7 — Validation (2 Scenarios)

### Scenario 1 — Successful Payment (End-to-End)

```
Order BC
  -> calls Payment.InitiatePayment(orderId=42, amount=Money{1999}, currency="INR")

Payment BC
  -> creates Payment{id=7, orderId=42, amount=1999, status=Initiated, gatewayName="stripe"}
  -> calls StripeGatewayAdapter.CreateCheckoutSession(orderId=42, amount=1999, currency="INR", metadata)
  -> receives {sessionToken="cs_xxx", checkoutUrl="https://checkout.stripe.com/cs_xxx"}
  -> stores sessionToken on Payment record
  -> returns checkoutUrl to caller

Shopper pays on Stripe-hosted page

Stripe fires: POST /webhooks/payment/stripe  (payload + Stripe-Signature header)

PaymentWebhookHandler
  -> calls StripeGatewayAdapter.VerifyWebhookSignature(payload, signature, secret) -> nil
  -> translates payload: GatewayStatus=Succeeded, gatewayRef="ch_yyy"
  -> calls PaymentSvc.OnPaymentCaptured(ctx, gatewayRef="ch_yyy", gatewayName="stripe")

PaymentSvc
  -> PaymentRepo.FindByGatewayRef("ch_yyy") -> Payment{id=7, status=Initiated}
  -> transitions status: Initiated -> Captured; sets capturedAt
  -> PaymentRepo.UpdateStatus(Payment{id=7, status=Captured})
  -> EventPublisher.Publish(PaymentCaptured{paymentId=7, orderId=42, amount=1999})

Order BC reacts to PaymentCaptured: transitions order 42 Pending -> Paid
Reporting BC reacts: records payment capture event
```

**Invariant check:** No shared tables between Payment and Order. Payment owns payments table; orderId is a reference only. One coarse-grained sync call at initiation + one async event at capture. OK.

### Scenario 2 — Admin Refund

```
Admin
  -> POST /api/v1/payments/7/refund  {amount: 500, reason: "Customer request"}
  -> Auth middleware validates JWT -> Admin identity confirmed

PaymentRestHandler
  -> calls PaymentSvc.RefundPayment(ctx, paymentId=7, amount=Money{500}, reason="Customer request")

PaymentSvc
  -> PaymentRepo.FindById(7) -> Payment{status=Captured, amount=1999}
  -> RefundAmountValidator.Validate(paymentId=7, newAmount=500)
     -> RefundRepo.SumIssuedRefunds(7) -> Money{0}  (no prior refunds)
     -> 0 + 500 = 500 <= 1999 -> valid
  -> StripeGatewayAdapter.RefundCharge(gatewayRef="ch_yyy", amount=500)
     -> returns gatewayRefundRef="re_zzz"
  -> creates Refund{id=1, paymentId=7, orderId=42, amount=500, status=Issued, gatewayRefundRef="re_zzz"}
  -> RefundRepo.Save(Refund{id=1})
  -> Payment.amount=1999, totalRefunded=500 < 1999 -> status: PartiallyRefunded
  -> PaymentRepo.UpdateStatus(Payment{id=7, status=PartiallyRefunded})
  -> EventPublisher.Publish(RefundIssued{refundId=1, paymentId=7, orderId=42, amount=500})

Order BC reacts to RefundIssued (e.g., adjusts order state) [Assumed]
Reporting BC reacts: records refund event
```

**Invariant check:** Payment owns all refund data. Refund amounts validated internally. Order BC does not reach into Payment tables. OK.

### Application Services

#### PaymentSvc

InitiatePayment(ctx context.Context, orderId int, amount shared.Money, currency string, metadata map[string]string) (Payment, checkoutUrl string, error)
- Creates Payment record (status: Initiated)
- Calls PaymentGatewayPort.CreateCheckoutSession
- Returns checkoutUrl to caller
- Errors: ErrPaymentAlreadyExists (idempotent on duplicate active orderId), ErrGatewayError

OnPaymentCaptured(ctx context.Context, gatewayRef string, gatewayName string) error
- Called by PaymentWebhookHandler after signature verification
- Finds Payment by gatewayRef; transitions Initiated -> Captured; sets capturedAt
- Publishes PaymentCaptured
- Errors: ErrPaymentNotFound, ErrInvalidTransition

OnPaymentFailed(ctx context.Context, gatewayRef string, reason string) error
- Transitions Initiated -> Failed; sets failedAt, failureReason
- Publishes PaymentFailed
- Errors: ErrPaymentNotFound, ErrInvalidTransition

RefundPayment(ctx context.Context, paymentId PaymentId, amount shared.Money, reason string) (Refund, error)
- Validates total refunds <= captured amount via RefundAmountValidator
- Calls PaymentGatewayPort.RefundCharge
- Creates Refund record; updates Payment status (Refunded or PartiallyRefunded)
- Publishes RefundIssued or RefundFailed
- Errors: ErrPaymentNotFound, ErrPaymentNotCaptured, ErrRefundExceedsAmount, ErrGatewayError

#### PaymentQuerySvc

GetPayment(ctx context.Context, paymentId PaymentId) (Payment, error)
GetPaymentByOrder(ctx context.Context, orderId int) (Payment, error)
ListRefunds(ctx context.Context, paymentId PaymentId) ([]Refund, error)

### Domain Services
| Service | Responsibility |
|---|---|
| RefundAmountValidator | Sums all Issued refunds for a payment via RefundRepo.SumIssuedRefunds and validates that the new refund amount does not cause the total to exceed the original captured amount. Pure domain logic — no gateway calls. |
| GatewaySignatureVerifier | Verifies HMAC/webhook signature from the gateway before processing any OnPaymentCaptured/OnPaymentFailed call. Lives in the webhook driving adapter (not the domain), but is a critical security boundary. [Inferred] |

### Capabilities
- Initiate gateway checkout sessions for placed orders
- Receive and process payment gateway webhooks (capture, failure) with signature verification
- Record full payment lifecycle with audit trail (timestamps, gateway refs, failure reasons)
- Process full and partial refunds via gateway with amount validation
- Publish payment lifecycle events consumed by Order BC and Reporting BC
- Isolate all PCI-scope gateway credentials, session tokens, and transaction data from other BCs
- Support swappable gateway adapters (ACL pattern) without domain model changes

### Ambiguous Questions — Needs Architect Input

1. [Needs Human] Gateway for v1: Stripe, Razorpay, or another? Determines which GatewayAdapter to build first and what credentials/config are needed. COD may also need a no-gateway path.

2. [Needs Human] Payment initiation trigger: Does Order.CheckoutSvc call Payment.InitiatePayment synchronously as part of checkout, or does Order publish OrderPlaced and Payment reacts asynchronously? Sync is simpler and ensures the checkoutUrl is available in the checkout response. Async requires the event bus and makes delivering the checkoutUrl to the shopper significantly harder.

3. [Needs Human] COD (Cash on Delivery) in v1: COD requires a separate flow with no gateway — e.g., PaymentSvc.MarkCODCollected(orderId) called by an admin when cash is received. Affects PaymentStatus, the gateway abstraction, and the CreateCheckoutSession contract.

4. [Needs Human] Multi-attempt payments: If payment fails, can the shopper retry (i.e., create a new Payment record for the same orderId)? Only one Payment can be Captured per order. Allowing retries means multiple Initiated/Failed records per orderId with a uniqueness constraint only on the Captured status.

5. [Needs Human] Partial refunds in v1: Affects RefundAmountValidator complexity, the PartiallyRefunded status, and API surface. If partial refunds are out of scope for v1, simplify to full-refund-only.

6. [Needs Human] Saved payment methods: Storing tokenized cards/UPI mandates for repeat customers? Requires a PaymentMethod entity and PCI-compliant tokenization. Recommended: out of scope for v1.
