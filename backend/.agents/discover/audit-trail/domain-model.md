## Step 1 — High-Level Domain Map

### Actors
- **Admin / Store Owner / Compliance Officer** — reviews who performed administrative changes, security modifications, or sensitive state overrides.
- **Upstream Bounded Contexts (All BCs)** — produce auditable mutation events or records whenever administrative actions, state transitions, or credential alterations occur.
- **Security / Compliance Monitoring Tools** — consumes query APIs or exports for compliance, intrusion detection, or forensics.

### Key Insight: Application Logging (Zerolog) vs. Audit Trail
- **Zerolog (Application / Tech Logging)**: Operational, technical, ephemeral diagnostics intended for engineers and sysadmins (e.g., debug logs, stack traces, latency, connection timeouts).
- **Audit Trail (Domain / Business Compliance)**: Immutable, structured historical records capturing **who** did **what**, **when**, on **which aggregate**, and **why** (e.g., "Admin Kasun changed product variant SKU-101 price from $20 to $15 at 14:02 UTC from IP 192.168.1.5").

### Business Flows Touching Audit Trail

1. **Administrative Mutation Logging**: Admin creates/updates products, modifies prices, edits coupons, alters settings, or forces order cancellations. [Inferred — critical for store integrity]
2. **Security & Identity Auditing**: Login failures, password changes, role assignments, account deactivations/reactivations, API key rotations. [Inferred — security compliance]
3. **Financial & Fulfillment Mutations**: Manual payment captures/refunds, shipment status overrides, manual inventory level adjustments. [Inferred — reconciliation tracking]
4. **Historical Compliance Search & Inspection**: Store owner or auditor filters audit entries by actor, target entity, date range, or action type via Admin dashboard. [Assumed — core capability of audit subsystem]
5. **Retention & Archival**: Old audit logs are sealed or exported according to legal/compliance retention policies. [Assumed]

### External Systems
- **Log Archival / SIEM (Optional Future)**: S3/Cold storage or security information systems (e.g., Datadog, Elastic).

## Step 3 — Boundary Analysis & Clustering

### Problem Signals & Boundary Justification
- **Append-Only / Immutability Requirement**: Audit trail records must be strictly append-only; nobody—not even admins—can update or delete an audit log entry. This is radically different from mutable domain entities.
- **Different Consistency Model**: Audit recording can happen asynchronously via events or fire-and-forget background workers so failure to write an audit trail does not abort user checkout, while still guaranteeing eventual delivery.
- **Regulatory and Forensic Boundary**: Isolates compliance queries and historical change records from production operational databases.
- **Generic Capability**: An audit log is a cross-cutting, generic enterprise necessity across all e-commerce domains.

## Step 8 — Document the Result

### Bounded Context Canvas

## Bounded Context: Audit Trail

- **Purpose**: Provides an append-only, tamper-evident historical log of administrative actions, security events, and critical business state mutations across the entire platform for compliance, security, and accountability.
- **Classification**: Generic

### Entities

- **AuditEntry** — Aggregate root representing an immutable audit log record.
  - `id` (AuditEntryId)
  - `timestamp` (time.Time)
  - `actor` (Actor: `{id, kind, displayName, ipAddress, userAgent}`)
  - `contextName` (string, e.g. "Product", "Pricing", "Order", "Auth")
  - `entityName` (string, e.g. "ProductVariant", "Promotion", "User")
  - `entityId` (string)
  - `action` (ActionType: `CREATE | UPDATE | DELETE | TRANSITION | SECURITY`)
  - `reason` (string, optional note provided by admin)
  - `changeSet` (ChangeSet: `{before: JSON/map, after: JSON/map}`)
  - `metadata` (map[string]string: `{traceId, correlationId, ...}`)

### Value Types

- **AuditEntryId** — `string` (opaque, time-sortable ID e.g., UUIDv7 or ULID)
- **ActorKind** — enum: `Admin | Customer | System`
- **Actor** — `{id string, kind ActorKind, displayName string, ipAddress string, userAgent string}`
- **ActionType** — enum: `Create | Update | Delete | Transition | Security`
- **ChangeSet** — `{before map[string]any, after map[string]any}`
- **AuditFilter** — `{actorId?, contextName?, entityName?, entityId?, action?, fromDate?, toDate?}`

### Application Services

- **AuditTrailSvc**
  - `Record(ctx, RecordAuditCmd)` -> `(AuditEntryId, error)`
    - Validates and persists an immutable audit entry.
  - `GetEntry(ctx, entryId)` -> `(AuditEntry, error)`
    - Fetches a single audit entry with its full before/after diff.
  - `Query(ctx, filter AuditFilter, pagination shared.Pagination)` -> `(AuditPage, error)`
    - Returns paginated audit trail for admin inspection.

### Domain Services

- **ChangeDiffComputer** — Utility that calculates before/after diffs between two struct/map states to produce a clean `ChangeSet`.

### Adapters

| Side | Adapter | Purpose |
|---|---|---|
| Driven | `AuditEntryRepo` | Append-only database adapter (inserts and read-only queries; no UPDATE or DELETE allowed) |
| Driving | `AuditEventConsumer` | Listens to audited domain events from upstream BCs and calls `AuditTrailSvc.Record` |
| Driving | `AuditAdminRestHandler` | Exposes read-only inspection endpoints under `/api/v1/admin/audit-logs` |

### Ubiquitous Language

| Term | Definition |
|---|---|
| AuditEntry | A single immutable, tamper-evident record of a mutation or security event |
| Actor | The entity that initiated the action (Admin, Customer, or System) |
| ChangeSet | The before-and-after state capture of affected fields |
| ActionType | The nature of the mutation (`Create`, `Update`, `Delete`, `Transition`, `Security`) |
| TargetEntity | The specific domain object being audited |
| Tamper-Evident | Guaranteed append-only storage where historical rows cannot be altered |

### Capabilities

- Record tamper-evident, append-only logs of administrative modifications and sensitive operations
- Capture who (actor), what (target entity & diff), when (timestamp), where (IP/agent), and why (reason)
- Provide filtered, paginated search over audit records for store administrators
- Support security forensic analysis and compliance auditing
- Isolate audit persistence from regular operational database tables

### Inbound

- Commands handled:
  - `RecordAuditEntry(actor, context, entity, entityId, action, before, after, metadata)`
  - `QueryAuditLogs(filter, pagination)`
  - `GetAuditEntry(id)`
- Events consumed:
  - Consumes sensitive domain events across all BCs (e.g. `UserRoleChanged`, `ProductArchived`, `VariantPriceChanged`, `OrderForceCancelled`, `PaymentRefunded`, `SettingChanged`).

### Outbound

- Events published:
  - `AuditEntryRecorded {entryId, contextName, action, actorId}` (Low priority, for real-time alerting)
- APIs / queries exposed:
  - REST (admin read-only): `/api/v1/admin/audit-logs`, `/api/v1/admin/audit-logs/:id`

### Dependencies

- **Upstream**:
  - All functional BCs (Auth, Product, Pricing, Order, Payment, Shipping, Settings) — provide domain events and audit triggers. Pattern: **Customer-Supplier**.
- **Downstream**:
  - Admin UI / Reporting (consumers of audit records). Pattern: **OHS / PL**.

### Data Owned

- `audit_entries` (strictly append-only table)
