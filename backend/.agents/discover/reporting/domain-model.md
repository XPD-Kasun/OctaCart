## Step 1 — High-Level Domain Map

### Actors

- **Admin / Merchant** — views dashboards, sales summaries, product performance, customer cohorts, and financial reports via the admin UI.
- **All upstream BCs** — publish domain events that Reporting consumes to build its read models.
- **Reporting BC itself** — runs scheduled aggregations (e.g., daily revenue roll-ups) via background workers.

### Key Insight: Reporting is a Pure Read Model

Reporting BC never writes to any other BC's tables. It consumes domain events from all upstream BCs, projects them into denormalised read models optimised for querying, and exposes query APIs. It is strictly a downstream consumer — it has no commands that mutate business state.

### Business Flows Touching Reporting

1. **Sales Analytics**: Track orders placed, paid, fulfilled, cancelled over time. Revenue by product, category, and period. [Inferred — context-map: Order → Reporting]
2. **Product Performance**: Top-selling variants, stock adjustment history, publish/archive trends. [Inferred — context-map: Product → Reporting]
3. **Customer Cohort Analytics**: New registrations over time, deactivations, repeat purchase rates. [Inferred — context-map: Customer → Reporting]
4. **Payment & Refund Tracking**: Captured payments, failed payments, refunds issued per period. [Inferred — context-map: Payment → Reporting]
5. **Shipping & Fulfillment Analytics**: Dispatch rates, delivery success rates, return rates. [Inferred — context-map: Shipping → Reporting]
6. **Pricing & Promotions Analytics**: Promotions activated/expired, coupon redemption rates, revenue impact of discounts. [Inferred — context-map: Pricing → Reporting]
7. **Review Analytics**: Review submission volume, approval/rejection rates, average ratings by product. [Inferred — context-map: Review → Reporting]

## Step 3 — Boundary Analysis

### Why a separate Reporting BC?

| Heuristic | Evidence |
|---|---|
| Different consistency model | Reporting can be eventually consistent (async event consumption); transactional BCs need strong consistency |
| Different data shape | Reporting stores denormalised, pre-aggregated projections; transactional BCs store normalised operational data |
| Different rate of change | Analytics query patterns evolve independently of business logic |
| Different scaling needs | Read-heavy query workloads need different indexing strategies than write-heavy transactional tables |
| Single ownership | A data/analytics team can own Reporting without touching Order, Product, or Payment logic |
| No shared writable tables | Reporting only writes to its own projection tables — never to any upstream BC's tables |

### Should Reporting be split further (e.g., Sales vs. Inventory reporting)?

No, for V1. The volume is too small to justify splitting. A single Reporting BC with distinct read-model tables per domain area (sales, inventory, customers, payments, shipping) is sufficient.

## Step 4 — Classification

**Reporting** — **Supporting**

Reporting is business-specific (merchant needs store-specific analytics) but is not the competitive differentiator. It supports merchant decision-making. It is not Generic because it must understand the business domain concepts (OrderLine, ShipmentStatus, CouponRedeemed) to project meaningful reports.

## Step 7 — Validation

### Scenario 1 — Admin views sales dashboard for last 30 days

1. Admin calls `GET /api/v1/admin/reporting/sales?period=Last30Days`.
2. `ReportingQuerySvc.GetSalesSummary(ctx, shopId, Last30Days)` queries the `sales_projections` table.
3. Returns `SalesSummary {totalRevenue, totalOrders, avgOrderValue, cancelRate}`.
   - No read into Order BC's operational tables. OK
   - Pre-aggregated projection; single fast query. OK
   - Order BC changes (e.g., new status added) require only a new event handler in Reporting. OK

### Scenario 2 — OrderCancelled event arrives, Reporting updates its projection

1. Order BC publishes `OrderCancelled {shopId, orderId, grandTotal, reason}`.
2. Reporting's `DomainEventConsumer` receives the event.
3. `ProjectionUpdater.HandleOrderCancelled` updates `sales_projections`: increments `cancelCount`, decrements `activeRevenue`.
4. Next dashboard query reflects the cancellation immediately (or within eventual consistency window).
   - No write to Order BC tables. OK
   - Reporting's projection can be rebuilt from scratch by replaying events (event sourcing property). OK
   - Single responsibility: Reporting decides how to project; Order BC has no reporting logic. OK

## Bounded Context: Reporting

- **Purpose**: Builds and maintains denormalised read-model projections from domain events across all upstream bounded contexts, and exposes query APIs for merchant analytics dashboards — covering sales, product performance, customer growth, payments, shipping, promotions, and reviews.
- **Classification**: Supporting

---

### Entities (Projection Read Models)

> These are not traditional domain aggregates. They are append-friendly, query-optimised projection tables. They do not enforce business invariants.

- **SalesProjection** — Aggregated sales data per shopId + time bucket.
  - `shopId` (ShopId), `bucketDate` (date), `orderCount` int, `paidCount` int, `cancelCount` int, `revenue` (Money), `refundTotal` (Money), `avgOrderValue` (Money)

- **ProductPerformanceProjection** — Per-variant sales data.
  - `shopId` (ShopId), `variantId`, `productId`, `bucketDate` (date), `unitsSold` int, `revenue` (Money), `returnCount` int, `stockDelta` int

- **CustomerGrowthProjection** — Customer registration trends.
  - `shopId` (ShopId), `bucketDate` (date), `newRegistrations` int, `deactivations` int

- **PaymentProjection** — Payment and refund aggregates.
  - `shopId` (ShopId), `bucketDate` (date), `capturedCount` int, `capturedTotal` (Money), `failedCount` int, `refundCount` int, `refundTotal` (Money)

- **ShippingProjection** — Shipping performance data.
  - `shopId` (ShopId), `bucketDate` (date), `dispatchedCount` int, `deliveredCount` int, `failedCount` int, `returnCount` int

- **PromotionProjection** — Promotion and coupon impact.
  - `shopId` (ShopId), `promoId`, `redemptionCount` int, `totalDiscountGranted` (Money), `revenueOnPromoOrders` (Money)

- **ReviewProjection** — Review volume and sentiment per product.
  - `shopId` (ShopId), `productId`, `bucketDate` (date), `submitted` int, `published` int, `rejected` int, `withdrawn` int, `ratingSum` int, `ratingCount` int

---

- `ShopId` — string (opaque; scopes all projections per store)

- `RevenuePoint` — `{bucketDate date, revenue Money, orderCount int}`
- `SalesSummary` — `{totalRevenue Money, totalOrders int, avgOrderValue Money, cancelRate float64, refundRate float64}`
- `PaymentSummary` — `{capturedCount int, capturedTotal Money, failedCount int, refundCount int, refundTotal Money}`

- **ReportingQuerySvc** (read-only; all methods require `shopId`)

  - `GetTopProducts(ctx, shopId, period Period, limit int)` → `([]ProductStat, error)`
  - `GetOrderStatusBreakdown(ctx, shopId, period Period)` → `(map[OrderStatus]int, error)`

  - `GetPaymentSummary(ctx, shopId, period Period)` → `(PaymentSummary, error)`
  - `GetRefundSummary(ctx, shopId, period Period)` → `(RefundSummary, error)`
  - `GetShippingPerformance(ctx, shopId, period Period)` → `(ShippingPerformanceSummary, error)`

### Domain Services

- **PeriodResolver** — Converts a named `Period` enum into concrete `(from time.Time, to time.Time)` range. Handles timezone using store timezone from Settings (or UTC as default). [Assumed]
- **BucketAssigner** — Assigns a domain event timestamp to the correct `bucketDate` based on granularity (day/week/month). Ensures projection rows are idempotent on replay.

### Ambiguous Questions Needed From Architect

1. **[Needs Human] Projection storage engine**: Should Reporting projections use the same relational DB as other BCs, or a separate read-optimised store (e.g., TimescaleDB, ClickHouse, or a separate PostgreSQL schema)? For V1 at small scale, the same DB with dedicated tables is simplest.
2. **[Needs Human] Event replay / projection rebuild**: If a projection gets corrupted or a new report is added, can the system replay all historical domain events to rebuild projections? This requires events to be persisted (event store or outbox table), not just fired in-process and discarded.
3. **[Needs Human] Dashboard timezone**: Should report time buckets use UTC or the store's configured timezone (from Settings BC)? Affects `PeriodResolver` and bucket assignment logic.
4. **[Needs Human] Real-time vs. near-real-time**: Are projections updated synchronously on each event (in-process, immediate consistency) or via an async worker queue (near-real-time, slight lag)? For V1, synchronous in-process update is simplest.
5. **[Assumed] No raw event log in Reporting**: Reporting stores only aggregated projections, not individual event records. Drill-down to individual orders uses the Order BC's own query APIs.
6. **[Assumed] No cross-store reporting**: All reports are scoped to a single shopId. Merchant-level cross-store aggregation is out of scope for V1.
