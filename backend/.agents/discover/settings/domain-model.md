## Step 1 — High-Level Domain Map

### Actors

- **Admin / Merchant** — configures store-level settings from the admin dashboard (store profile, currency, tax model, contact details, domain).
- **Downstream BCs (Product, Order, Pricing, Notifications, Extension)** — read settings as stable published configuration; they are consumers, not actors.

### Business Flows Touching Settings

1. **Store Profile Setup**: Admin sets store name, description, logo, timezone, and country. [Inferred — referenced as upstream in context-map for Product, Order, Pricing, Notifications, Extension]
2. **Currency Configuration**: Admin sets the store currency code (e.g., INR, USD). Downstream BCs treat currency as read-only config. [Inferred — all Money-using BCs reference Settings for currency]
3. **Tax Configuration**: Admin sets tax inclusion model (tax-inclusive vs. exclusive) and default tax jurisdiction/rate. Pricing BC consumes this to initialise tax rules. [Inferred — context-map: Settings → Pricing for jurisdiction defaults]
4. **Contact & Notification Branding**: Admin sets sender email address, sender name, support URL. Notifications BC uses these in every outgoing message. [Inferred — context-map: Settings → Notifications for sender email, company name, support links]
5. **Order Behaviour Configuration**: Admin configures order number prefix, low-stock threshold, and whether guest checkout is allowed. [Assumed — common small-seller store config]
6. **Domain Configuration**: Admin sets the store's public domain URL. Extension BC uses this for webhook signature headers. [Inferred — context-map: Settings → Extension for store domain URL]

### External Systems

None. Settings is purely internal; it is a configuration source, not an integration endpoint.

## Step 3 — Boundary Analysis

### Why a separate Settings BC?

| Heuristic | Evidence |
|---|---|
| Cross-cutting consumer | 5+ BCs consume store config; centralising avoids duplicating config tables |
| Different rate of change | Store name and currency change rarely; product catalog and orders change constantly |
| Different domain expert | Store owner configures global settings; order or catalog team should not own this |
| Stable published language | Settings exposes a read-only config contract (OHS/PL) to all consumers — a real boundary |
| Data ownership | Only Settings BC writes to store_settings; all other BCs read |

### Is it really a BC or just a config table?

It is both. The boundary exists because: (a) it owns a distinct data aggregate (StoreSettings), (b) it has its own application service and admin REST surface, (c) it emits an auditable domain event, and (d) at least 5 other BCs declare it as an upstream dependency. That is sufficient for a boundary even if the domain logic is thin.

## Step 7 — Validation

### Scenario 1 — Admin updates store currency from INR to USD

1. Admin calls `UpdateCurrencySettings(shopId, "USD")`.
2. Settings BC updates `StoreSettings.currencyCode = "USD"`.
3. Publishes `SettingsUpdated {shopId, section: "Currency", changedKeys: ["currencyCode"]}`.
4. Audit Trail ingests the event.
5. Downstream BCs (Product, Pricing, Order) either re-read settings on next call or invalidate cached config.
   - Settings owns the single source of truth for currency. No shared table with Product or Order. OK
   - One event emitted; downstream BCs decide when to re-read. OK
   - Settings can evolve (add more currency options, multi-currency future) without touching Order internals. OK

### Scenario 2 — Notifications BC renders a dispatch email

1. Shopper order dispatched → Notifications receives ShipmentDispatched event.
2. Notifications calls `Settings.GetSettings(ctx, shopId)` → `StoreSettings`.
3. Extracts `senderEmail`, `senderName`, `supportUrl`.
4. Renders email template with store branding.
   - Read-only call; no shared writable table. OK
   - Coarse-grained: one settings fetch per notification batch (cacheable). OK
   - Changing store branding requires no change to Notifications BC logic. OK

## Bounded Context: Settings

- **Purpose**: Provides a single, shopId-scoped source of truth for store-level configuration — including store profile, currency, tax model, contact branding, order behaviour, and domain — consumed as a stable published language by all downstream bounded contexts.
- **Classification**: Generic

---

### Entities

- **StoreSettings** — Aggregate root. One record per shop.
  - `shopId` (ShopId), `storeName`, `storeDescription?`, `logoUri?`, `timezone`, `country`, `currencyCode` (CurrencyCode), `taxInclusion` (TaxInclusionModel), `defaultTaxRate?` (Percentage), `defaultJurisdiction?`, `senderEmail`, `senderName`, `supportUrl?`, `supportPhone?`, `orderPrefix?`, `lowStockThreshold` int, `allowGuestCheckout` bool, `storeDomain?`, `adminDomain?`, `createdAt`, `updatedAt`

---

### Value Types

- `ShopId` — string (opaque; received from Auth JWT claim)
- `CurrencyCode` — string, ISO 4217 (e.g., `"INR"`, `"USD"`)
- `TaxInclusionModel` — enum: `Inclusive | Exclusive`
- `Percentage` — int basis points (e.g., 1800 = 18%)
- `SettingsSection` — enum: `StoreInfo | Currency | Contact | Tax | Order | Domain`

---

### Application Services

- **SettingsSvc**
  - `GetSettings(ctx, shopId ShopId)` → `(StoreSettings, error)` — read-only; called by downstream BCs and admin dashboard
  - `InitialiseSettings(ctx, shopId ShopId)` → `(StoreSettings, error)` — creates a default settings record when a new store is provisioned; idempotent
  - `UpdateStoreInfo(ctx, shopId, input UpdateStoreInfoCmd)` → `(StoreSettings, error)` — storeName, description, logo, timezone, country
  - `UpdateCurrencySettings(ctx, shopId, currencyCode CurrencyCode)` → `error`
  - `UpdateContactSettings(ctx, shopId, input UpdateContactCmd)` → `error` — senderEmail, senderName, supportUrl, supportPhone
  - `UpdateTaxSettings(ctx, shopId, input UpdateTaxCmd)` → `error` — taxInclusion, defaultTaxRate, defaultJurisdiction
  - `UpdateOrderSettings(ctx, shopId, input UpdateOrderCmd)` → `error` — orderPrefix, lowStockThreshold, allowGuestCheckout
  - `UpdateDomainSettings(ctx, shopId, input UpdateDomainCmd)` → `error` — storeDomain, adminDomain
  - Errors: `ErrSettingsNotFound`, `ErrInvalidCurrencyCode`, `ErrInvalidTimezone`, `ErrInvalidEmail`

---

### Domain Services

- **SettingsValidator** — Validates field-level constraints on update commands (valid ISO 4217 code, valid IANA timezone, valid email format). Pure domain logic; no external calls.

### Capabilities

- Initialise default store settings when a new store is created
- Allow admin to configure store profile, currency, tax model, contact branding, order behaviour, and domain
- Provide a stable, read-only GetSettings contract to all downstream BCs (OHS/PL)
- Emit SettingsUpdated events for Audit Trail on every mutation

---

### Inbound

- Commands handled: `InitialiseSettings`, `GetSettings`, `UpdateStoreInfo`, `UpdateCurrencySettings`, `UpdateContactSettings`, `UpdateTaxSettings`, `UpdateOrderSettings`, `UpdateDomainSettings`
- Events consumed: None

---

### Outbound

- Events published:
  - `SettingsUpdated {shopId, section SettingsSection, changedKeys []string}` — consumed by Audit Trail
- APIs exposed:
  - REST (admin): `GET /api/v1/admin/settings` — returns full StoreSettings
  - REST (admin): `PATCH /api/v1/admin/settings/store-info`
  - REST (admin): `PATCH /api/v1/admin/settings/currency`
  - REST (admin): `PATCH /api/v1/admin/settings/contact`
  - REST (admin): `PATCH /api/v1/admin/settings/tax`
  - REST (admin): `PATCH /api/v1/admin/settings/order`
  - REST (admin): `PATCH /api/v1/admin/settings/domain`

### Dependencies

- **Upstream**:
  - Auth BC — admin identity for all mutation endpoints. Pattern: **OHS / PL**.
- **Downstream (serves)**:
  - Product BC — currency code. Pattern: **OHS / PL**.
  - Order BC — currency code, AllowGuestCheckout. Pattern: **OHS / PL**.
  - Pricing BC — currency code, tax jurisdiction defaults. Pattern: **OHS / PL**.
  - Notifications BC — senderEmail, senderName, supportUrl. Pattern: **OHS / PL**.
  - Extension BC — storeDomain. Pattern: **OHS / PL**.
  - Audit Trail — consumes SettingsUpdated. Pattern: **Customer-Supplier**.

---

### Data Owned

- `store_settings` — one row per `shopId`

> Settings does NOT own currency exchange rates, product prices, or tax rates. It owns only the store-level configuration defaults that other BCs consume.

### Ambiguous Questions Needed From Architect

1. **[Needs Human] Settings initialisation trigger**: When is `InitialiseSettings` called — by the Auth/merchant registration flow, or by the first admin login to the store? This determines the coupling point between store provisioning and Settings BC.
2. **[Needs Human] AllowGuestCheckout**: Confirm this lives in Settings and is consumed by Order BC at checkout. Alternatively, it could live in Order BC directly.
3. **[Needs Human] Settings caching strategy**: Downstream BCs will call `GetSettings` on every relevant request. Should Settings expose a caching hint (e.g., ETag / last-modified), or should each BC cache the settings in-process for a configurable TTL?
4. **[Needs Human] Multi-currency future**: Is the `currencyCode` field intended to remain a single currency for V1 with multi-currency added later, or is multi-currency already in scope? V1 assumption: single currency per store.
5. **[Assumed] One settings record per shop**: There is exactly one `StoreSettings` aggregate per `shopId`. No versioning or history of settings changes is stored in this BC (Audit Trail handles history).
