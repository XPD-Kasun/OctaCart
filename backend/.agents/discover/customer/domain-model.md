## Step 1 — High-Level Domain Map

### Actors
- **Shopper / Buyer** — self-registers, manages their own profile, address book, and views order history.
- **Seller / Admin** — may view or search customer records; may manually adjust notes or tags (CRM lite).
- **Order BC** — reads customer shipping/billing address snapshot at checkout.
- **Auth BC** — provides identity (UserId) on which the Customer profile is anchored.

### Key Insight: Customer vs. User (Auth)

Auth owns the **identity record** — credentials, claims, lockout, OIDC provider link. That is a security boundary.
Customer owns the **shopper profile** — who they are as a buyer: name, contact details, saved addresses, preferences, and their relationship with the store.

The split is justified by:
- Different rates of change: password/claims are security-sensitive and audited; display name and address change casually.
- Regulatory boundary: PII (name, address, phone) and payment data should be isolated from auth tokens.
- Different domain experts: security/auth team vs. CRM/merchandising team.
- `Auth.User` has `Name` and `Email` today — this is a known overlap that needs resolution (see Ambiguous Questions).

### Business Flows Touching Customer

1. **Registration**: Shopper signs up via form or OIDC -> Auth creates a User -> Customer BC creates a CustomerProfile linked to that UserId. [Inferred — Auth already creates User; Customer profile creation is the next step]
2. **Profile Management**: Shopper updates display name, phone number, profile picture. [Assumed — standard e-commerce need]
3. **Address Book Management**: Shopper adds, edits, deletes saved addresses; marks one as default. [Inferred — context-map.md and shipping.md: "Customer owns the editable address book"]
4. **Checkout Address Supply**: Order BC reads the chosen address from Customer to snapshot onto an order. [Inferred — context-map: Customer -> Order (Customer-Supplier)]
5. **Order History View**: Shopper views their past orders. [Assumed — read projection, data owned by Order; Customer BC provides a query port or Order exposes it]
6. **Account Deactivation**: Admin or shopper deactivates account. [Assumed — GDPR/right to erasure consideration]

### External Systems
- **Auth BC** — upstream identity provider; Customer reads UserId from Auth token. Pattern: OHS/PL.

## Step 3 — Boundary Analysis

### Candidate 1 — Merge Customer into Auth BC

Auth already holds Name and Email on User. Could attach address book there.

**Problems:**
- Auth is Generic (security commodity). Polluting it with address book, preferences, and CRM data creates a dangerous big-ball-of-mud security boundary.
- Different rates of change: auth credentials are rarely updated; shopping addresses change frequently.
- Auth BC should have minimal scope to pass security audits — adding PII widens the audit surface.
- shared/types.go already distinguishes UserId (auth identity) from ActorType=Customer (domain role) — the codebase signals these are different concerns.

**Verdict**: Reject.

### Candidate 2 — Dedicated Customer BC (recommended)

Customer = "the shopper as a buyer" — profile, address book, preferences. Auth = "the shopper as a principal" — identity, credentials, claims.

Boundary heuristics:

| Heuristic | Evidence |
|---|---|
| Different rates of change | Auth credentials: rarely; address book: frequently |
| Regulatory / PII boundary | PII isolation from security system limits audit scope |
| Different domain experts | Auth/security team vs. CRM/merchandising team |
| Polyseme Customer | Auth: an authenticated principal. Customer BC: a shopper with a buying history and preferences |
| Data ownership | Address book and profile are writable only by Customer BC |
| Workflow handoff | Registration handoff: Auth creates identity -> Customer creates profile |

**Verdict**: Customer is a distinct Supporting BC.

Customer profile and address management is business-specific but not OctaCart's core competitive differentiator. It supports the Order flow by supplying addresses and supports CRM-lite capabilities.

## Step 7 — Validation

### Scenario 1 — Shopper Registers and Places First Order
1. Shopper submits registration form. Auth creates User (UserId=42, email, passwordHash).
2. Auth publishes UserCreated or returns UserId to the driving adapter.
3. Driving adapter calls Customer.RegisterCustomer(userId=42, email, name).
4. Customer creates CustomerProfile {customerId, userId=42, name, email, createdAt}.
5. Shopper proceeds to checkout. Order calls Customer.GetAddress(customerId, addressId=nil) -> returns default address or prompts user.
6. Order snapshots the address into the order. Customer's address book is unchanged.
   - Customer owns address exclusively. No shared table with Order. OK
   - One coarse-grained call: Order -> Customer.GetAddress. OK
   - CustomerProfile can evolve (add preferences, avatar) without touching Order. OK

### Scenario 2 — Shopper Updates Shipping Address After Order
1. Shopper edits their saved address in the account dashboard.
2. Customer.UpdateAddress(customerId, addressId, newAddress) -> AddressUpdated.
3. Existing orders are unaffected — they hold immutable address snapshots.
4. Future orders will use the new address.
   - Address mutation is entirely within Customer BC. OK
   - Order has no dependency on Customer's live address after checkout. OK
   - Shipping has its own immutable destination snapshot — no coupling. OK

### Scenario 3 — Admin Deactivates a Customer Account
1. Admin calls Customer.DeactivateAccount(customerId).
2. Customer marks the profile as Deactivated; publishes AccountDeactivated.
3. Auth BC receives the event (or is called) to revoke active sessions for that UserId.
4. Order BC can still read historical orders (they reference customerId, not the live profile).
   - Customer owns its deactivation state. OK
   - Auth session revocation is a downstream reaction; loose coupling via event. OK
   - Order history is read-only against the customerId reference — boundary intact. OK

## Bounded Context: Customer

- **Purpose**: Manages the shopper's identity within the store — profile details, saved address book, wishlist, and marketing preferences — and supplies address data to the Order BC at checkout.
- **Classification**: Supporting

---

### Entities

- **CustomerProfile** — Aggregate root.
  - `id` (CustomerId), `userId` (shared.UserId — foreign key into Auth), `firstName`, `lastName`, `displayName`, `phone?`, `email` (contact email, may differ from login email), `avatarUri?`, `status` (Active | Deactivated), `marketingConsent bool`, `createdAt`, `updatedAt`

- **Address** — A saved address-book entry.
  - `id` (AddressId), `customerId`, `label?` (e.g., "Home", "Office"), `recipientName`, `line1`, `line2?`, `city`, `province?`, `postalCode`, `country`, `phone?`, `isDefault bool`

- **WishlistItem** — A product variant saved for later by the customer.
  - `id` (WishlistItemId), `customerId`, `variantId` (reference into Product BC — read-only), `addedAt`
  > WishlistItem carries only the variantId reference. No price is stored — current price is always fetched live from Product/Pricing when displaying the wishlist.

---

### Value Types

- `CustomerId` — string (opaque, DB-generated)
- `AddressId` — string (opaque, DB-generated)
- `WishlistItemId` — string (opaque, DB-generated)
- `CustomerStatus` — enum: `Active | Deactivated`
- `AddressSnapshot` — `{recipientName, line1, line2?, city, province?, postalCode, country, phone?}` — read-only value object returned to Order BC; does NOT include AddressId or customerId

---

### Application Services

- **CustomerSvc** (primary)
  - `RegisterCustomer(ctx, userId shared.UserId, firstName, lastName, email string)` -> `(CustomerProfile, error)` — creates profile after Auth registration; idempotent on duplicate userId
  - `UpdateProfile(ctx, customerId, UpdateProfileCmd)` -> `(CustomerProfile, error)` — mutable fields: firstName, lastName, displayName, phone, email, avatarUri, marketingConsent
  - `DeactivateAccount(ctx, customerId)` -> `error` — soft-delete; publishes AccountDeactivated
  - `ReactivateAccount(ctx, customerId)` -> `error` — admin action to undo deactivation
  - Errors: `ErrCustomerNotFound`, `ErrCustomerAlreadyExists`, `ErrCustomerDeactivated`, `ErrInvalidStatus`

- **AddressSvc**
  - `AddAddress(ctx, customerId, AddAddressInput)` -> `(Address, error)` — first address auto-set as default
  - `UpdateAddress(ctx, customerId, addressId, UpdateAddressCmd)` -> `(Address, error)`
  - `DeleteAddress(ctx, customerId, addressId)` -> `error` — blocked if it is the only address and there are open orders [Needs Human]
  - `SetDefaultAddress(ctx, customerId, addressId)` -> `error`
  - `GetAddressSnapshot(ctx, customerId, addressId?)` -> `(AddressSnapshot, error)` — returns the specified or default address as an immutable value object for Order BC
  - Errors: `ErrAddressNotFound`, `ErrCannotDeleteOnlyAddress`, `ErrCustomerNotFound`

- **CustomerQuerySvc** (reads — admin dashboard and storefront)
  - `GetCustomer(ctx, customerId)` -> `(CustomerProfile, error)`
  - `GetCustomerByUserId(ctx, userId shared.UserId)` -> `(CustomerProfile, error)` — called after Auth login to resolve customerId
  - `ListCustomers(ctx, filter CustomerFilter, page shared.Pagination)` -> `([]CustomerProfile, error)`
  - `ListAddresses(ctx, customerId)` -> `([]Address, error)`

- **WishlistSvc**
  - `AddToWishlist(ctx, customerId, variantId)` -> `(WishlistItem, error)` — no-op if already present (idempotent)
  - `RemoveFromWishlist(ctx, customerId, wishlistItemId)` -> `error`
  - `ListWishlist(ctx, customerId)` -> `([]WishlistItem, error)` — caller enriches with live price/availability from Product/Pricing
  - `ClearWishlist(ctx, customerId)` -> `error`
  - Errors: `ErrWishlistItemNotFound`, `ErrCustomerNotFound`, `ErrCustomerDeactivated`

### Dependencies

- **Upstream**:
  - Auth BC — provides `shared.UserId` after registration; Customer profile is anchored to it. Pattern: **Customer-Supplier** (Customer is downstream of Auth for identity).
- **Downstream (serves)**:
  - Order BC — reads `AddressSnapshot` at checkout via `GetAddressSnapshot`. Pattern: **Customer-Supplier** (Customer is upstream).

### Ambiguous Questions Needed From Architect

1. **[Needs Human] Name field duplication**: `Auth.User` currently stores `Name` and `Email`. Should those fields be removed from Auth.User and live only in Customer? Auth.User.Name is only needed for display; the auth concern is identity/claims. Removing it from Auth keeps the security model lean but requires a Customer read whenever a name is needed.
2. **[Needs Human] Registration trigger mechanism**: Is Customer.RegisterCustomer triggered by the REST driving adapter immediately after Auth.FormAuthSvc.CreateProfile succeeds (synchronous, in the same HTTP handler), or by consuming a UserCreated domain event from Auth (async)? The async approach is cleaner but requires an event bus.
3. **[Needs Human] DeleteAddress guard**: Should deleting the last address be blocked unconditionally, blocked only if there are active/open orders, or allowed freely? Affects ErrCannotDeleteOnlyAddress logic.
4. **[Needs Human] Guest checkout**: Does OctaCart v1 support guest checkout (no Customer profile required)? If yes, Order must handle a null customerId and address is entered inline. If no, registration is mandatory before checkout.
5. **[Needs Human] Marketing consent**: Is marketing consent (email opt-in) within scope for v1, or deferred? Affects CustomerProfile fields and any notification/email integration.
6. **[Assumed] Contact email vs. login email**: Customer.email is the display/contact email; Auth.User.email is the login credential. They start equal at registration but a customer could update the contact email independently. If this is wrong and they must always be the same, Customer should not store email — it should always read from Auth.
7. **[Assumed] No loyalty / rewards**: No points, tiers, or wallet in Customer BC at this scope. If loyalty is added it would either extend Customer or become a new Loyalty BC.
8. **[Assumed] Wishlist is per-customer, single list**: One wishlist per customer; no named lists. If named lists are required in future, WishlistItem gains a `listId` field.
