## Step 1 — High-Level Domain Map

### Actors
- **Shopper / Customer** — browses products, builds a cart, applies a coupon, checks out, pays, and tracks the order.
- **Seller / Admin** — reviews placed orders, marks orders as fulfilled (packed and ready to ship), cancels or refunds orders.
- **Product BC** — upstream supplier of variant data, stock availability, and price-change events.
- **Pricing BC** — upstream price resolver; provides PricedLine and coupon validation at checkout.
- **Customer BC** — upstream address supplier; provides AddressSnapshot at checkout.
- **Payment BC** — downstream payment processor; Order initiates and awaits payment.
- **Shipping BC** — downstream fulfillment handler; receives fulfilled order data; provides rate quotes upstream.
- **Reporting BC** — downstream event consumer for analytics.

### Key Insight: Cart is the Pre-Order State

Cart is not a Customer concern. Cart lives entirely within the Order flow:
- Cart knows about variants, quantities, applied coupons, and resolved prices.
- Cart -> Checkout -> Order is a single lifecycle managed by Order BC.
- A cart may be anonymous (guest) or linked to a customerId.
- The transition from Cart to Order is an atomic operation within Order BC.

### Business Flows

1. **Cart lifecycle**: Shopper adds/removes variants to cart, applies a coupon, gets live price quotes (from Pricing) and shipping quotes (from Shipping). [Assumed — standard e-commerce checkout]
2. **Checkout**: Cart is frozen into an Order — addresses snapshotted from Customer, prices confirmed from Pricing, stock reserved from Product. [Inferred — context-map: Customer->Order, Product->Order, Pricing->Order]
3. **Payment initiation**: Order initiates payment with Payment BC; awaits PaymentCaptured event. [Inferred — context-map: Order->Payment]
4. **Fulfilment**: Admin marks the order as Fulfilled (packed) → Shipping BC creates a shipment. [Inferred — context-map: Order->Shipping]
5. **Cancellation / Refund**: Admin or shopper cancels an order before fulfilment; refund flows through Payment. [Assumed]
6. **Order history**: Shopper and admin query orders by various filters. [Assumed]

## Step 3-4 — Boundary & Classification

One context: **Order** — cart, checkout, order lifecycle, and fulfilment state machine.
Splitting Cart from Order was considered and rejected: they share the same language (LineItem, Qty, Price snapshot), same domain expert (order management), and Cart -> Order is an in-BC state transition.

**Classification**: Core — Order is the central revenue-generating flow of the platform.

| Term | Cart/Order context | Product context | Pricing context | Shipping context |

## Step 7 — Validation

### Scenario 1 — Shopper Checks Out a Cart
1. Shopper has CartId=77 with 2x VariantA.
2. Shopper calls Checkout(cartId=77, shippingAddressId=5, shippingMethodId=2, customerId=42).
3. Order BC calls Customer.GetAddressSnapshot(42, 5) -> AddressSnapshot (immutable).
4. Order BC calls Pricing.ResolveCart(lines, destination) -> DiscountedCart with PricedLines.
5. Order BC calls Product.CheckStock(variantA, qty=2) -> ok.
6. Order BC creates Order with immutable LineItems (price snapshots locked), AddressSnapshot.
7. Publishes OrderPlaced. Cart is invalidated.
   - No shared tables with Customer, Product, or Pricing. OK
   - Three coarse-grained calls, then an event. OK
   - Cart can change (add/remove) without touching Product's catalog. OK

### Scenario 2 — Payment Captured, Order Fulfilled, Shipped
1. Payment BC captures payment -> publishes PaymentCaptured {orderId}.
2. Order receives event -> transitions OrderStatus: Pending -> Paid.
3. Admin calls FulfillOrder(orderId) -> OrderStatus: Paid -> Fulfilled.
4. Order publishes OrderFulfilled {orderId, shippingAddress, lineItems}.
5. Shipping BC reacts -> creates Shipment, generates label, marks Dispatched.
6. Shipping publishes ShipmentDispatched {orderId, trackingNumber}.
7. Order receives event -> OrderStatus: Fulfilled -> Dispatched.
   - Each BC owns its own state. Order owns OrderStatus; Shipping owns ShipmentStatus. OK
   - Events are coarse-grained. OK
   - Shipping can change internal label logic without Order caring. OK

### Scenario 3 — Order Cancelled Before Fulfilment
1. Shopper calls CancelOrder(orderId) -> Order checks status (must be Pending or Paid).
2. If Paid: Order calls Payment.Refund(orderId, amount) or publishes RefundRequested event.
3. Order transitions OrderStatus -> Cancelled.
4. Order releases stock reservation in Product BC (via event or call).
5. Publishes OrderCancelled {orderId, customerId, refundAmount}.
   - Order owns the cancellation decision; Payment owns the refund mechanics. OK
   - Stock release is a separate concern (Product BC receives StockReleased or ReserveStock reversal). OK

## Bounded Context: Order

- **Purpose**: Manages the full purchase lifecycle — from a shopper building a cart through checkout, payment confirmation, and fulfilment — ensuring that prices, addresses, and stock are locked at the moment of purchase.
- **Classification**: Core

---

### Entities

- **Cart** — A transient pre-order aggregate.
  - `id` (CartId), `customerId?` (nil for guest), `lines []CartLine`, `couponCode?`, `createdAt`, `updatedAt`, `expiresAt?`

- **CartLine** — One intent-to-purchase entry in a cart.
  - `id` (CartLineId), `cartId`, `variantId`, `qty`
  > No price stored — resolved live from Pricing BC on demand.

- **Order** — The central aggregate; immutable after placement.
  - `id` (OrderId), `customerId?`, `status` (OrderStatus), `lines []OrderLine`, `shippingAddress` (AddressSnapshot), `billingAddress?` (AddressSnapshot), `shippingMethodId`, `shippingCost` (Money), `subtotal` (Money), `discountAmount` (Money), `taxAmount` (Money), `grandTotal` (Money), `couponCode?`, `notes?`, `placedAt`, `updatedAt`

- **OrderLine** — An immutable line within an order.
  - `id` (OrderLineId), `orderId`, `variantId`, `qty`, `unitPrice` (Money — PriceSnapshot), `lineTotal` (Money)

- **StockReservation** — A hold placed on product stock at checkout; released on payment failure or cancellation.
  - `id` (ReservationId), `orderId`, `variantId`, `qty`, `status` (Held | Confirmed | Released), `createdAt`

---

### Value Types

- `CartId`, `CartLineId`, `OrderId`, `OrderLineId`, `ReservationId` — string (opaque, DB-generated)
- `Money` — int64 minor units (from shared.Money)
- `OrderStatus` — enum: `Pending | Paid | Fulfilled | Dispatched | Delivered | Cancelled | ReturnReceived`
- `ReservationStatus` — enum: `Held | Confirmed | Released`
- `AddressSnapshot` — `{recipientName, line1, line2?, city, province?, postalCode, country, phone?}` — immutable value; snapshot taken from Customer BC at checkout; stored on Order
- `PriceSnapshot` — `Money` — unit price locked at checkout from Pricing.ResolveCart; stored on OrderLine

---

### Application Services

- **CartSvc**
  - `GetOrCreateCart(ctx, customerId?)` -> `(Cart, error)` — returns existing active cart or creates a new one; guest carts identified by CartId in session
  - `AddItem(ctx, cartId, variantId, qty)` -> `(Cart, error)` — validates variant exists via Product port; merges qty if line already present
  - `UpdateItemQty(ctx, cartId, cartLineId, qty)` -> `(Cart, error)` — qty=0 removes the line
  - `RemoveItem(ctx, cartId, cartLineId)` -> `error`
  - `ApplyCoupon(ctx, cartId, couponCode, customerId?)` -> `(Cart, error)` — delegates validation to Pricing BC
  - `RemoveCoupon(ctx, cartId)` -> `error`
  - `MergeGuestCart(ctx, guestCartId, customerId)` -> `(Cart, error)` — on login, merge guest cart lines into customer cart [Needs Human]
  - `GetCartSummary(ctx, cartId, customerId?)` -> `(CartSummary, error)` — calls Pricing.ResolveCart + Shipping.QuoteRates; returns resolved prices + shipping options; NOT persisted
  - Errors: `ErrCartNotFound`, `ErrVariantNotFound`, `ErrCartExpired`, `ErrInsufficientStock`, `ErrCouponInvalid`

- **CheckoutSvc**
  - `Checkout(ctx, CheckoutCmd)` -> `(Order, error)` — atomic: snapshots address, resolves prices, checks stock, creates Order, invalidates Cart, publishes OrderPlaced
    - `CheckoutCmd`: `{cartId, customerId?, shippingAddressId?, inlineAddress?, shippingMethodId, billingAddressId?, notes?}`
  - Errors: `ErrCartNotFound`, `ErrCartEmpty`, `ErrInsufficientStock`, `ErrAddressRequired`, `ErrPricingUnavailable`, `ErrShippingMethodInvalid`

- **OrderSvc** (lifecycle management)
  - `FulfillOrder(ctx, orderId)` -> `error` — Admin: Paid -> Fulfilled; publishes OrderFulfilled
  - `CancelOrder(ctx, orderId, reason, actorId)` -> `error` — Pending or Paid -> Cancelled; releases stock reservation; publishes OrderCancelled
  - `OnPaymentCaptured(ctx, orderId, amount Money)` -> `error` — internal; Pending -> Paid; confirms stock reservation
  - `OnPaymentFailed(ctx, orderId, reason)` -> `error` — internal; releases stock reservation; publishes OrderPaymentFailed
  - `OnShipmentDispatched(ctx, orderId, trackingNumber)` -> `error` — internal; Fulfilled -> Dispatched
  - `OnShipmentDelivered(ctx, orderId)` -> `error` — internal; Dispatched -> Delivered
  - `OnReturnReceived(ctx, orderId)` -> `error` — internal; Delivered -> ReturnReceived
  - Errors: `ErrOrderNotFound`, `ErrInvalidTransition`, `ErrAlreadyCancelled`, `ErrAmountMismatch`

- **OrderQuerySvc** (reads)
  - `GetOrder(ctx, orderId)` -> `(Order, error)`
  - `GetOrderByCustomer(ctx, customerId, page shared.Pagination)` -> `([]Order, error)`
  - `ListOrders(ctx, filter OrderFilter, page shared.Pagination)` -> `([]Order, error)` — admin
  - `GetCartSummary(ctx, cartId, customerId?)` -> `(CartSummary, error)` — read model: enriched cart with live prices

---

### Domain Services

- **CheckoutOrchestrator** — Coordinates the atomic checkout: (1) lock cart, (2) fetch address snapshot, (3) call Pricing.ResolveCart, (4) check/reserve stock, (5) create Order, (6) invalidate Cart. Rolls back stock reservation on any failure.
- **OrderStatusMachine** — Enforces legal transitions between OrderStatus states; rejects invalid transitions with ErrInvalidTransition.
- **StockReservationManager** — Holds, confirms, and releases stock reservations via ProductPort; ensures no oversell.

- Maintain a shopping cart (add, update, remove items; apply coupon)

### Ambiguous Questions Needed From Architect

1. **[Needs Human] Guest cart merge strategy**: When a guest (anonymous) shopper logs in, how are conflicts between a guest cart and an existing customer cart resolved? Options: (a) guest cart wins and replaces customer cart, (b) merge lines (add quantities), (c) keep both and let shopper choose. This affects MergeGuestCart logic significantly.
2. **[Needs Human] Stock reservation model**: Is stock reserved at checkout (before payment) using a synchronous ReserveStock call into Product BC, or is availability only checked optimistically (no reservation) and confirmed post-payment? Optimistic avoids complexity but allows oversell during payment processing window.
3. **[Needs Human] Guest checkout support**: Confirmed as a question in Customer BC — if guest checkout is supported, Order must handle null customerId and accept an inline address instead of a customerId lookup.
4. **[Needs Human] Refund initiation**: When CancelOrder is called on a Paid order, does Order directly call Payment.Refund (synchronous), or does it publish OrderCancelled and let Payment react asynchronously? Affects failure handling.
5. **[Needs Human] Cart expiry**: Should carts auto-expire after inactivity (e.g., 30 days)? If yes, a background job or TTL mechanism is needed. Affects CartRepo and Cart entity.
6. **[Needs Human] VariantPriceChanged handling**: When a variant price changes while it is in an active cart, should the cart silently update (shopper sees new price on next view), show a warning, or force re-confirmation at checkout? Currently the CartLine stores no price so the next GetCartSummary call will reflect the new price automatically — this may need a user-facing notification.
7. **[Assumed] 1 Order per Cart**: A cart is converted to exactly one order at checkout. Partial orders (split from one cart) are out of scope for v1.
8. **[Assumed] Payment gateway is external to Order BC**: Order only knows about initiating payment and reacting to events. The external gateway integration lives inside Payment BC.
