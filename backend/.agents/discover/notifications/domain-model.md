## Step 1 — High-Level Domain Map

### Actors
- **Customer / Shopper** — recipient of transactional updates (order placed, payment received, shipment dispatched, order delivered).
- **Seller / Admin** — recipient of operational alerts (new order arrived, low stock alert) and manages store notification templates/preferences.
- **Upstream Bounded Contexts** — publish domain events or commands that trigger customer or admin communication.
- **Third-party Notification Providers** — external SMTP/SES providers, SMS gateways, push notification services.

### Business Flows Touching Notifications

1. **Transactional Customer Order Communications**: Order placed, payment confirmed, order cancelled, refund issued. [Inferred — standard e-commerce customer journey]
2. **Fulfillment & Delivery Alerts**: Tracking number added, shipment dispatched, out for delivery, successfully delivered, delivery failed. [Inferred — context-map Shipping and Order flows]
3. **Account & Identity Alerts**: Welcome email on registration, password reset link/token, account deactivation confirmation. [Inferred — Auth/Customer lifecycle]
4. **Merchant Operational Alerts**: Low stock threshold reached, critical payment failure or chargeback alert, new order notification. [Assumed — common small seller convenience]
5. **Template Rendering and Delivery**: Message content is rendered with context data (order items, customer name) into recipient-friendly HTML/text and sent through delivery gateways with status tracking. [Inferred]

## Step 3 — Boundary Analysis & Clustering

### Problem Signals & Boundary Justification
- **Different Rate of Change**: Email/SMS rendering, delivery provider swapping, subject line tweaks, and retry backoffs change independently of order fulfillment or inventory decrement.
- **Generic Commodity Nature**: Sending an email or SMS via an external provider is generic plumbing across software domains.
- **Third-party Failure Isolation**: External communication gateway outages, rate limits, and network latency should never block core transactional workflows (e.g., checkout or payment capture).
- **Separation of PII & Message Audit**: Delivery logs, bounce tracking, and rendered message history belong in a dedicated log/audit store, separate from order business state.

## Step 7 — Validation of Boundaries

- [x] **Single Team / Component Ownership**: A developer can maintain email templates and provider adapters without touching order or customer logic.
- [x] **Data Ownership**: Notifications BC exclusively owns notification records, delivery attempt logs, and template definitions.
- [x] **Language Consistency**: Words like `Template`, `Recipient`, `Dispatch`, `Channel`, and `DeliveryStatus` are uniform and distinct from order lines or cart items.
- [x] **Coarse-Grained Integration**: Triggered via async events or simple enqueue commands (`template_key`, `recipient`, `payload_data`).
- [x] **Autonomous Evolution**: Switching from local SMTP to AWS SES or adding SMS notifications requires zero changes in Order, Payment, or Customer BCs.

## Step 8 — Document the Result

### Bounded Context Canvas

## Bounded Context: Notifications

- **Purpose**: Centralizes the rendering, formatting, and delivery of transactional and operational messages across communication channels (email, SMS) to customers and administrators.
- **Classification**: Generic

### Entities

- **Notification** — The aggregate root representing a dispatched or queued message.
  - `id` (NotificationId)
  - `shopId` (ShopId) — _shopId received from the upstream domain event payload; used for template scoping and delivery log partitioning._
  - `recipient` (Recipient)
  - `channel` (Channel)
  - `templateKey` (string)
  - `subject` (string)
  - `body` (string)
  - `status` (NotificationStatus: `Pending | Sending | Sent | Failed`)
  - `attempts` (int)
  - `lastError` (string, optional)
  - `metadata` (map[string]string)
  - `createdAt`, `sentAt`
- **NotificationTemplate** — The template used to render notifications.
  - `id` (TemplateId)
  - `key` (string, unique e.g., `order_confirmation`, `password_reset`)
  - `channel` (Channel)
  - `subjectTemplate` (string)
  - `bodyTemplate` (string)
  - `updatedAt`

### Value Types

- **NotificationId** — `string` (opaque unique identifier)
- **TemplateId** — `string` (opaque unique identifier)
- **ShopId** — string (opaque; extracted from consumed event payloads; not owned by Notifications BC)
- **Channel** — enum: `Email | SMS` (V1 focuses on `Email`)
- **Recipient** — `{destination string, name string?}`
- **NotificationStatus** — enum: `Pending | Sending | Sent | Failed`
- **TemplatePayload** — `map[string]any` / key-value dictionary passed for template substitution

### Application Services

- **NotificationSvc**
  - `SendNotification(ctx, SendNotificationCmd)` -> `(NotificationId, error)`
    - Queues or synchronously delivers a notification given a template key, recipient, and payload.
  - `RetryFailed(ctx, notificationId)` -> `error`
    - Re-attempts delivery for a failed notification.
  - `GetNotification(ctx, notificationId)` -> `(Notification, error)`
- **TemplateSvc**
  - `GetTemplate(ctx, key, channel)` -> `(NotificationTemplate, error)`
  - `UpdateTemplate(ctx, UpdateTemplateCmd)` -> `error`

### Domain Services

- **TemplateRenderer** — Evaluates template strings (e.g., Go `html/template` or `text/template`) with domain event payload data to produce subject and body.

### Adapters

| Side | Adapter | Purpose |
|---|---|---|
| Driven | `NotificationRepo` | Persists notifications and delivery logs |
| Driven | `TemplateRepo` | Persists notification templates (DB or embedded files) |
| Driven | `EmailSender` (ACL) | Adapter interfacing with SMTP / AWS SES / third-party email provider |
| Driven | `SmsSender` (ACL) | Optional adapter for SMS gateways |
| Driving | `DomainEventSubscriber` | Listens to events from Order, Payment, Shipping, Auth, Customer BCs and enqueues notifications |
| Driving | `NotificationWorker` | Background job / worker to process pending notifications and handle retries |
| Driving | `NotificationRestHandler` | Admin endpoints for inspecting delivery status and editing templates |

### Ubiquitous Language

| Term | Definition |
|---|---|
| Notification | An outbound communication instance addressed to a specific recipient |
| Channel | Medium of transmission (Email, SMS) |
| Template | Parameterized text or HTML structure identified by key |
| Recipient | Intended receiver contact address and display name |
| Dispatch | The process of rendering and forwarding to the external gateway |
| Delivery Status | Current transmission state (`Pending`, `Sending`, `Sent`, `Failed`) |
| Provider | External transmission network/service (e.g. SMTP server) |

### Capabilities

- Render and format parameterized customer and admin notifications
- Send transactional emails via pluggable provider adapters (SMTP / SES)
- Maintain an audit trail of sent communications and error logs
- Retry transient delivery failures with backoff
- Allow admin customization of notification templates

### Inbound

- Commands handled:
  - `SendNotification(templateKey, recipient, payload)`
  - `RetryFailed(notificationId)`
  - `UpdateTemplate(templateKey, channel, subject, body)`
- Events consumed:
  - From Order: `OrderPlaced`, `OrderCancelled`
  - From Payment: `PaymentCaptured`, `RefundIssued`
  - From Shipping: `ShipmentDispatched`, `ShipmentDelivered`, `DeliveryFailed`
  - From Customer: `CustomerRegistered`
  - From Auth: `PasswordResetRequested`
  - > **Note**: All consumed events carry shopId in their payload; Notifications BC threads shopId into the Notification record for traceability.

### Outbound

- Events published:
  - `NotificationSent {notificationId, channel, recipient, templateKey}`
  - `NotificationDeliveryFailed {notificationId, channel, recipient, reason}`
- APIs / queries exposed:
  - `GetNotification(notificationId)` -> `Notification`
  - REST (admin): `/api/v1/admin/notifications`, `/api/v1/admin/notifications/templates`

### Dependencies

- **Upstream**:
  - Auth BC, Order BC, Payment BC, Shipping BC, Customer BC — furnish events and triggers. Pattern: **Customer-Supplier**.
  - Settings BC — supplies store sender email, store name, and branding defaults. Pattern: **OHS / PL**.
- **Downstream**:
  - External Delivery Providers (SMTP, SES, etc.) — Pattern: **ACL**.

### Data Owned

- `notifications` (delivery history, recipient, status, attempts, errors) — _includes shopId for per-store delivery tracking._
- `notification_templates` (template key, subject, body, channel)
